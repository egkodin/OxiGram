# ADR 0002: GUI framework

- Status: accepted (the owner chose gpui after the numbers below)
- Date: 2026-10-26

## Context

Telegram Desktop draws all of its widgets itself. rgram needs a GPU framework that
gives full control over rendering, good text (bidi, complex scripts, emoji,
selection), IME and HiDPI, on macOS, Linux and Windows. Candidates measured on
the same scene:

- **iced 0.14.0** (crates.io, released 2025-12-07; wgpu renderer, tiny-skia
  software fallback).
- **gpui 0.2.2** (crates.io, published 2025-10-22). This is a year-old snapshot:
  gpui is developed inside Zed's monorepo and has not been republished.
- **gpui at Zed `876c1b0`** (git, 2026-10-25), the version rgram would actually
  depend on. Its API already differs from 0.2.2 (`Application::new()` is gone;
  apps start through `gpui_platform::application()`), and it needs Rust 1.98.1+.

## Method

The spike code lived outside the repository and was deleted after the decision;
this section is the record.

- Scene: 10,000 chat messages generated from a fixed seed (identical content in
  every build): 12 authors, 1 to 160 words each, with bold, italic, link and
  monospace spans, Cyrillic text and color emoji; author name on the first
  message of a run, a 33 px avatar with initials on the last; bubbles capped at
  430 px; Open Sans 13 px from `lib_ui/fonts`; 1000×800 logical window,
  bottom-anchored. Rendering checked with an in-app screenshot (iced).
- Virtualization: gpui's built-in `list()` with `ListAlignment::Bottom`. iced has
  no virtual list, so the spike implemented one as a custom `Widget` (~250
  lines): items are built and laid out only around the viewport, child state
  trees persist per item so text is not reshaped every frame, and the scroll
  position is an anchor (item index plus offset from the viewport bottom).
- Run: release build with Rust 1.99.1 (`lto = "fat"`, `codegen-units = 1`,
  `panic = "abort"`, `strip = true`; `panic = "abort"` worked in all three).
  After the first frame: 2 s of warm-up, then 60 s of automatic scrolling
  towards older messages at 3,000 px/s, driven per frame from the frame
  timestamp (the wheel-scroll code path: no app-level messages, no view rebuild
  in iced). The window is kept above other windows, because macOS stops frame
  callbacks for occluded windows; an earlier batch without this produced a
  stalled run and footprints taken from a hidden window.
- Frame timing comes from runs without memory sampling (`vmmap` suspends the
  process for ~0.5 s). Memory comes from separate runs that sample `vmmap`
  physical footprint (what Activity Monitor shows) at scroll start, at 30 s and
  at 57 s. `ps` RSS is not used: on macOS it counts resident pages of shared
  system frameworks and disagreed with the footprint by up to 70 MB.
- "Frame build" is the CPU time to produce a frame, but not the same span in
  both: gpui's covers `render` through `paint` for the whole window; iced's
  covers the list widget's `layout` and `draw`. Process CPU % is the comparable
  cost figure. "Late frames" counts draw-to-draw intervals above 9.375 ms
  (1.5 frame periods).
- Machine: Mac mini, Apple M4 (10 cores), 24 GB, macOS 27.0.1, external 4K
  display at 160 Hz with 2× scaling (6.25 ms frame period). Start-up is from
  `exec` to the first draw, warm page cache. Three runs per configuration;
  the table gives medians, ranges in parentheses.
- All three were measured again in one session after the correction below; the
  table holds only that batch. The cold-start row and the tiny-skia figures are
  from the first batch.

### Correction

The first batch built gpui@git with `gpui_platform`'s default features. On macOS
that leaves out `font-kit`, and gpui then falls back to a text system that draws
no text, so that column measured a scene without text (18.5 % CPU, 7.96 ms p99,
167 MB). gpui 0.2.2 and iced were not affected. The gpui@git spike was rebuilt
with `font-kit` (confirmed with `cargo tree -e features`) and every configuration
re-measured. The text itself was not checked on screen: the shell lacked the
screen-recording permission `screencapture` needs.

iced's software renderer (tiny-skia), same scene: 91 fps instead of 160, one core
at 100 %, footprint ~98 MB. It is a usable fallback, not a primary path.

Observations:

- All three hold the 160 Hz cadence on average. The gap is in the tail: gpui@git
  is the only one inside the 8 ms p99 budget (gpui 0.2.2 misses it by 0.03 ms).
  Both gpui builds have about a tenth of iced's late frames.
- iced's tail comes from synchronous text shaping in `layout` when a long message
  enters the overscan (frame build max 13 ms). That part is in the spike's list
  widget and could be amortized (shape ahead of the viewport under a per-frame
  time budget), so it is not a hard limit of iced.
- About 90 MB of iced's footprint while scrolling is GPU memory owned by
  `iced_wgpu`. Its glyph atlas (`cryoglyph`) grows on demand and `trim()` only
  clears the in-use set, so the atlas never shrinks; changing that means patching
  `iced_wgpu`. One of three runs peaked at 190 MB. Even so, iced is the leanest:
  3–4 MB under gpui@git while scrolling and 23 MB at idle.
- The baseline footprint of any of them at 4K/2× is 170–180 MB while rendering,
  before TDLib is loaded. The budget of 150 MB idle RSS on the chat list must be
  re-based on footprint in M1 (`docs/perf.md`); RSS is the wrong metric on macOS.

## Non-numeric comparison

| | gpui @ git | iced 0.14 |
|---|---|---|
| Releases | None since 0.2.2; pin a Zed commit, update deliberately | crates.io, semver; 0.14 is 10 months old, `master` active |
| API stability | Churns (bootstrap API changed within a year) | Stable within a release |
| Toolchain | Rust ≥ 1.98.1; macOS build needs Xcode's Metal toolchain (839 MB download) or the `runtime_shaders` feature | Rust ≥ 1.88 |
| Renderers | Metal (macOS), DirectX 11 (Windows), wgpu (Linux: Vulkan, GL) | wgpu everywhere, tiny-skia fallback |
| Text stack | Platform: CoreText, DirectWrite, cosmic-text on Linux (closest to Qt's per-platform rendering in tdesktop) | cosmic-text everywhere (same output on every OS) |
| Virtual list | Built in, bottom-aligned, variable height | Must be written (done in the spike) |
| IME | Full (Zed's editor) | `InputMethod` API, newer |
| Accessibility | AccessKit integrated (macOS, Linux) | Not in a release (draft PR) |
| Architecture fit | Entities and views, `Rc`-based, single UI thread; the unidirectional flow (update, reduce, state, view) is ours to enforce | Elm (message, update, view): the unidirectional flow is the framework's own model |
| License | Apache-2.0 | MIT |

## Decision

**gpui, pinned to Zed commit `876c1b0`** (`gpui` and `gpui_platform` as git
dependencies with `rev`), because it leads on the frame-time metrics the budgets
are written in: CPU while scrolling (-25 % against iced) and p99 frame time (the
only one inside 8 ms, with a tenth of iced's late frames). It also brings
accessibility, mature IME and a bottom-anchored virtual list, which rgram would
otherwise build. It costs memory: 3–4 MB more than iced while scrolling and
23 MB more at idle.

The project's rule was "on equal results, pick iced". The results were not equal,
so the owner decided, accepting the costs below. The owner chose on the first
batch, which overstated gpui@git (see Correction); the corrected numbers keep its
lead on CPU and frame time and reverse the memory comparison.

## Consequences

- The pin lives once, in `[workspace.dependencies]`. Moving it is a deliberate
  change in its own commit: bump `rev`, fix the API breakage, re-run the scroll
  and idle measurements, and note the new commit here.
- The toolchain follows Zed's (`rust-toolchain.toml` pins the same channel).
- `gpui_platform` is used with the features Zed itself enables: `font-kit`
  (macOS text) and `wayland` and `x11` (Linux windows and text). Without them
  gpui builds, runs and silently draws no text.
- macOS builds compile Metal shaders with Xcode's Metal toolchain. The app's
  `runtime-shaders` feature compiles them at startup instead; CI builds with
  `--all-features`, so its macOS runners need no Metal toolchain, and the
  precompiled path is checked only on developer machines.
- Linux builds need the system headers gpui links against (Wayland, X11/xkbcommon,
  fontconfig, Vulkan loader); CI installs them from Zed's own `script/linux` list.
- Every fresh CI cache pulls a ~550 MB Zed checkout; CI caches `~/.cargo/git`.
- No software renderer: a machine without a working GPU driver cannot run rgram.
  rgram reports this as a startup error rather than a blank window.
- gpui does not impose the unidirectional flow (`Update -> reduce -> State ->
  view`). rgram enforces it in `model` and `features`: views read `State` and
  emit `Action`s; nothing else mutates state.
- The spike code was deleted; this ADR is the record of it.

## Not verified

- Linux and Windows builds of the spikes: there is no CI remote yet, and Docker
  was not available on this machine. Only macOS arm64 was built and measured.
  The M0 workspace carries the Linux and Windows checks forward into CI.
- gpui's first-launch (cold) start-up at `876c1b0`.
